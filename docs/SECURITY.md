# Security

## Threat model

The platform collects hostile data. The realistic risks, in order:

1. **Public exposure of OpenCTI.** An internet-facing OpenCTI with a weak password is a full CTI graph, including any sensitive reports, plus an API that can write to the graph.
2. **Credential leakage from the repository.** `.env` files, MISP keys and tokens committed by accident.
3. **Malicious feed content.** Indicator values are untrusted strings; they are rendered escaped and defanged.
4. **Snapshot over-sharing.** A collector change that copies sensitive fields into the public JSON.
5. **Host compromise via the USB disk / hypervisor.** Out of scope for the app, but the reason the platform is segmented.

## Exposure model

| Surface | Reachable from | Auth |
|---|---|---|
| Radar/blog `:80` | LAN (or public if published) | none — read-only static |
| OpenCTI `:8443` | LAN | local account, session |
| MISP `:9443` | LAN | local account, API key |
| OpenCTI API `:8080` | loopback only | bearer token |
| Elasticsearch/Redis/RabbitMQ/S3 | Docker network only | service credentials |

**Do not port-forward 8443, 9443 or 8080.** If remote analyst access is needed, use Tailscale/WireGuard or a Cloudflare Tunnel with Access in front, not a raw forward.

## Secrets

- Generated by `scripts/gen-env.sh` and `scripts/gen-misp-env.sh` using `openssl rand`.
- Stored in `.env` and `misp/.env`, mode `600`, owned by the deploy user.
- `.gitignore` excludes `.env`, `misp/.env`, `misp/ssl/`, `site/node_modules`, `site/dist`.
- Never paste a token into a briefing, screenshot, issue or commit. If one leaks, rotate it; deleting the commit is not enough.

Check before every push:

```bash
git status --short
git grep -nE 'OPENCTI_ADMIN_TOKEN=[0-9a-f-]{36}|MISP_API_KEY=[0-9a-f-]{36}' -- . ':!*.example' || true
```

## OpenCTI hardening

Current state is a lab bootstrap: connectors use the admin token. Harden in this order:

1. **Create a service account for connectors.** In OpenCTI, create a user with a role that can manage connectors but not administration, then issue a token per connector. Put each token in `.env` and reference it in the connector's `OPENCTI_TOKEN`.
2. **Create a read-only token for the collector.** The collector only queries; a read-only role limits the blast radius of a compromised web host.
3. **Disable open registration.** `Settings → Security` — ensure only admins can create users.
4. **Enforce MFA** on the admin account if the build supports it; otherwise keep the UI LAN-only.
5. **Rotate the bootstrap token** after the first week.
6. **Set `APP__TELEMETRY__ENABLED=false`** (already done).
7. **Review connector scopes.** Remove connectors you do not use; every connector is another credential and another parser processing untrusted input.

## MISP hardening

- The automation key is scoped to the admin user created at first boot. Create a dedicated sync user with the minimum role and use its key for OpenCTI.
- Keep `MISP_SSL_VERIFY=false` only because the certificate is self-signed. On a real domain, issue a proper certificate and turn verification on.
- Disable feeds you do not consume. Each enabled feed is bandwidth, disk and parsing.
- `MISP_ENFORCE_WARNING_LIST=true` on the connector drops attributes that match known false-positive lists.
- Do not enable MISP's public-facing registration or guest access.

## Publication rules (TLP)

The public snapshot is **TLP:CLEAR only**. Enforced by:

- source selection — public OSINT feeds and public reporting;
- the MISP connector's TLP/distribution filter;
- the collector's explicit field allow-list;
- defanging in the browser;
- excluding victim identities and personal data.

If a sensitive source is added later, it must be tagged above TLP:CLEAR and excluded in `collect_radar.py`. The collector currently does not filter by marking definition because every enabled source is public; **if that changes, add a marking filter before the first non-public feed is connected.**

## Snapshot review checklist

Before publishing a new field or source:

- [ ] Is the field derived from a public source or reference data?
- [ ] Could it identify a victim, a person or an internal host?
- [ ] Is the indicator defanged in the UI?
- [ ] Does the source licence permit redistribution?
- [ ] Is the value escaped before insertion into HTML? (The site uses `escapeHtml` for feed values.)

## Static site

- No cookies, no analytics, no third-party JS except Google Fonts and CARTO tiles. Self-host both if you need a zero-third-party deployment.
- CSP is intentionally not set in the Caddyfile because Astro inlines styles and scripts. Add a hash-based CSP if you need one; test the map and charts after.
- The site never receives an OpenCTI token. If you add a live search feature, put it behind a server-side proxy with rate limiting — do not embed the token.

## Host

- Debian 13, unattended-upgrades for security patches.
- Docker daemon access is root-equivalent; only the deploy user is in the `docker` group.
- The VM disk is on a USB HDD in the lab. Treat physical access and bridge failure as availability risks, not confidentiality ones (volumes are not encrypted at rest).
- If the host is shared, enable disk encryption or move the VM to an encrypted NVMe dataset.

## Incident response (platform compromise)

1. **Isolate.** `docker compose stop` (or disconnect the VM NIC) — preserving volumes.
2. **Preserve.** Snapshot the VM in Proxmox before changing anything.
3. **Rotate.** All tokens, MISP keys, admin passwords, MinIO/RabbitMQ credentials.
4. **Assess.** OpenCTI audit log (`/dashboard/settings/audits`), Caddy access logs, Docker events, `auth.log`.
5. **Rebuild if in doubt.** The graph is in Elasticsearch; a compromised app container may have written to it. Restore the last known-good backup, then re-ingest.
6. **Disclose.** If public data was altered, publish a correction. If credentials leaked, say so.

## Reporting a vulnerability

Use the repository's private security advisory channel. Do not open a public issue with exploit details or live credentials.
